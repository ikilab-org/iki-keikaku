# 全計画の俯瞰ページを生成する（設計）

作成 2026-08-13 ／ 対象 `tools/build.mjs`（新規）・`plans/all/`（新規）・`assets/palette.css`（新規）

README「フェーズ2」の第2段階です。第1段階（`data/plans.yml` にすべての計画を入れる）は
[2026-08-12 の設計](2026-08-12-zenkeikaku-bunrui.md)で完了し、76件が収録されています。

---

## 1. なぜ今これをやるか

**76件が構造化されたのに、それを見る手段がありません。** 現在の公開ページは福祉分野と介護保険の2本で、
どちらも手書きです。産業・教育・環境・インフラ・行財政の計画は、データには入っているのにページに出ていません。

そして手書きは限界に来ています。福祉ページの体系図・タイムライン・一覧は、**分野を1つ増やすたびに
手で直す**必要があります。76件を手書きで維持するのは現実的ではありません。

## 2. 決めたこと

| 論点 | 決定 |
|---|---|
| 成果物 | **全市の俯瞰ページ `plans/all/` を新設。** 既存ページの図と本文は手書きのまま残す（配色だけ差し替える） |
| 生成方式 | **ビルドして HTML をコミットする。** `tools/build.mjs` が `plans.yml` から `plans/all/index.html` を生成 |
| 実行時のJS | **データを組み立てる JS を使わない。** 図と表は HTML に書き出す（詳細は 4.4） |
| 配色 | **岡部・伊藤の Color Universal Design 推奨配色（8色）に統一。** 既存ページの色も差し替える |
| 俯瞰ページの中身 | **構造だけ。** 手書きの分析は入れず、深掘りは分野別ページの役割とする |

### 手書きの分析を入れない理由

既存の福祉ページの体系図には、基本理念・基本目標・所管・二重の位置づけといった**分析**が入っています。
これは `plans.yml` にない情報で、生成できません。

**生成物は網羅的で常に最新な代わりに、記述は薄くなります。** これを埋めようとして俯瞰ページに
手書きを混ぜると、生成部分と手書き部分が混在して、再生成のたびに手書きが失われる危険が出ます。

**役割を分けます。** 俯瞰ページは「76件がどう並んでいるか」を示し、
分野別ページは「その分野で何が起きているか」を論じます。

## 3. ページの構成

`plans/all/index.html` に3つの図を置きます。**すべて `data/plans.yml` から生成します。**

### 3.1 体系図

縦に階層の帯を並べ、各帯に計画をチップで置きます。チップの色は `domain`（大分類8つ）です。

| 帯 | 対象 | 件数 |
|---|---|---|
| 国・長崎県 | `level` が `national` / `prefectural` | 9 |
| 総合計画 | `tier: sougou` | 3 |
| 部門別基本計画 | `tier: bumon` | 22 |
| 個別計画 | `tier: kobetsu` | 21 |
| 実施・行動計画 | `tier: jisshi` | 11 |
| 施設・財産管理 | `tier: shisetsu` | 8 |
| 階層を確認できていない | `tier` 欠落（`todo` あり） | 1 |
| 社会福祉協議会 | `level: council` | 1 |

**帯は `level` を先に見て、市の計画だけ `tier` で分けます。** 社協の `csw-katsudou-2` は
`tier: bumon` を持っていますが、`level: council` なので社協の帯に入ります。
順序を逆にすると部門別基本計画に紛れ込みます。

**`tier` を確認できていない1件（`ondanka-jimu`）も帯を作って表示します。** 落とすと
「76件すべてが現れる」が崩れ、未調査が見えなくなります。

**階層は `tier` で表し、明示的な関係は注記として重ねます。** 理由は本数です。

```
parent 8本 ／ includes 2本 ／ embedded_in 2本 ／ conforms_to 2本
related 26本（延べ） ／ predecessors 7本 ／ successor 5本
```

67件の市計画に対して `parent` は8本しかありません。**線を引くと、ほとんどの計画が
どこにも繋がっていない図になります。** これは関係が無いのではなく、**まだ調べていない**からです
（`todo` が29件残っています）。

そこで**線を引かず**、体系図の下に**関係の本数を1つの表にまとめて**置きます。
「位置づけ上の上位計画が明示されているもの 8件 / 76件」のように分母を添え、
**本数の少なさが調査の進捗を表す**という読み方ができる形にします。

帯と帯のあいだの `.arrow` には、既存ページと同じく**関係の種類の名前だけ**を置きます
（「整合」「個別計画として位置づけ」など）。件数はここに書きません。

### 3.2 タイムライン

横軸を年度、縦を `domain` でグループ化した帯にします。データの実際の範囲は **2010〜2035年度**です。

**`domain` を持たない9件（すべて長崎県の計画）は、末尾に「国・長崎県」のグループを作って置きます。**
`domain` は市と社協の計画にだけ付ける決まりなので（`data/schema.md`）、これは欠落ではありません。
色は分野色ではなく `var(--muted)` を使います。

**この図の主な価値は、満了の集中が一目で分かることです。**

| 年度 | 満了する計画 |
|---|---|
| 令和8年度（2026） | **11件** |
| 令和11年度（2029） | **11件** |
| 令和10年度（2028） | 5件 |

令和8年度末の11件は、福祉分野の主要計画と県計画が同時に切れるものです。

**期間を持たない25件をどう扱うかが、この図の設計の要点です。**

- `period: { start: null, end: null }`（随時修正） … 地域防災計画など。**「随時修正」の帯を別に置く**
- `period` の欠落（未調査） … `todo` 付き。**「計画期間を確認できていない」の帯を別に置く**
- `status: planned`（未策定） … 期間が未定。**同上**

**この25件を図から落とすと、俯瞰したつもりで3分の1が見えていないことになります。**
帯を分けて、件数とともに必ず表示します。

### 3.3 一覧

`domain` ごとにセクションを分け、表にします。**`domain` を持たない9件は末尾の「国・長崎県」の節に置きます**
（3.2 と同じ扱い）。列は次のとおりです。

| 列 | 内容 |
|---|---|
| 計画名 | `name`。`url` があればリンク |
| 期間 | `period`。`null` は「随時修正」、欠落は「未確認」 |
| 階層 | `tier` のラベル |
| 法定性 | `statutory` のラベル。未記載は「未確認」 |
| 所管 | `department`。欠落は「未確認」 |
| 状態 | `status` のラベル |

**`todo` が立っている計画には印を付けます。** 空欄と「調べていない」を読み手が区別できるようにするためです。
これはデータ側の原則（`data/schema.md`「未調査の表し方」）を、そのまま画面に出すものです。

## 4. 生成の仕組み

### 4.1 `tools/build.mjs`

```bash
node tools/build.mjs            # plans/all/index.html を生成
node tools/build.mjs --check    # 生成結果が現在のファイルと一致するか検査（CI用）
```

**既存ツールと同じ流儀**にします。外部依存なし、`tools/yaml.mjs` でパース、CLI は直接実行のときだけ動く、
`--check` で exit 1 を返す。

**ビルドの先頭で `validate` を走らせます。** error があれば生成せずに終了します。
**壊れたデータからページを作らない**のが目的です。

### 4.2 テンプレートを分けない

ページ固有の文章（前書き・注記・フッタ）は `build.mjs` 内に持ちます。

別ファイルのテンプレートに切り出すと、**テンプレートとデータの整合を別途保証する必要が出ます。**
ページが1枚のうちは、スクリプト内に文字列で持つほうが追いやすくなります。
2枚目・3枚目を生成する段階になったら、そのとき共通化します。

### 4.3 生成物をコミットする

`plans/all/index.html` はリポジトリにコミットします。

- GitHub Pages にビルド工程を入れずに済む（`.nojekyll` で静的配信している現在の作りを維持）
- **差分で図の変化が追える。** 計画を1本足したときに何が変わるかがレビューできる
- ビルドが動かなくてもページは生き続ける

### 4.4 実行時の JS の扱い

**既存ページには `<script>` があります。** 「JS なし」ではありません。中身は2種類です。

| 用途 | 場所 | 俯瞰ページでの扱い |
|---|---|---|
| テーマ切替（7行、データを含まない） | 3ページすべて | **同じものを置く。** 他ページと操作を揃えるため |
| タイムラインと表の組み立て（データをJSリテラルで持ち `innerHTML` で描く） | `plans/fukushi` `plans/kaigo-7-9` | **置かない。** HTML に書き出す |

**2つ目が、生成に移す動機の一つです。** 既存ページは計画名も期間も HTML に存在せず、
JS を切ると空の枠だけが残ります。検索エンジンにも読まれません。
生成すれば内容が HTML に入るので、この問題が消えます。

## 5. 配色

### 5.1 CUD 配色に統一する

**現状は食い違っています。** 既存ページはそれぞれのファイルに色を重複して持っていて
（`index.html` と `plans/fukushi/` は7色 `--c1`〜`--c7`、`plans/kaigo-7-9/` は3色 `--c1`〜`--c3`）、
`data/schema.md` は「slot は岡部・伊藤の Color Universal Design 推奨配色セット（8色）に対応する」と
書いています。**この記述は 2026-08-12 の作業で入れたもので、実装と一致していません。**

CUD 配色に統一し、`data/schema.md` の記述を実態に合わせます。

### 5.2 `assets/palette.css` に切り出す

CUD の8色を1か所に定義し、俯瞰ページと既存ページの両方から読ませます。
現在は3ページがそれぞれ同じ色を重複して持っています。

**ライトとダークで別の値を持つ現在の作りは踏襲します。** CUD の原色をそのまま暗い地に置くと沈む色があるため、
既存ページは light `#2a78d6` / dark `#3987e5` のように調整しています。同じ考え方で、
**CUD の色相を保ったまま明度を調整した dark 用の値**を用意します。

### 5.3 slot への割り当て

CUD の標準的な並びは黒から始まります。**黒は本文と同じ色なので、分野色として先頭に置くと
最大の分野が本文と同じ色になります。** そこで**黒を末尾に回します。**

| slot | 分野 | 件数 | CUD の色（light） |
|---|---|---|---|
| 1 | 健康・福祉 | 17 | 青 `#0072B2` |
| 2 | 都市基盤・交通 | 13 | 朱 `#D55E00` |
| 3 | 産業・雇用 | 9 | 緑 `#009E73` |
| 4 | 市政総論 | 8 | 橙 `#E69F00` |
| 5 | 行財政運営 | 7 | 紫赤 `#CC79A7` |
| 6 | 教育・文化 | 6 | 空 `#56B4E9` |
| 7 | 防災・安全 | 4 | 黄 `#F0E442` |
| 8 | 生活環境 | 3 | 黒 `#000000` |

**黄（slot 7）は明るいので、白地に細い点として置くと見えません。** 塗りとして使い、文字は黒にします。
**黒（slot 8）は塗りに使い、文字を白抜きにします。** 点として使う箇所では輪郭を付けて地と区別します。

dark では、色相を保ったまま明度を上げた値を `palette.css` に別途定義します。
黒はダークの地に沈むため、**dark の slot 8 は明るいグレー**に置き換えます。

### 5.4 既存ページの差し替え

`plans/fukushi/index.html` と `plans/kaigo-7-9/index.html` の色を差し替えます。

**既存ページは `category`（小分類）で塗り分け、俯瞰ページは `domain`（大分類）で塗り分けます。**
同じ色が別のものを指すことになりますが、これは 2026-08-12 の設計 3.1 で決めた2階層の帰結です
（「ハブページは大分類で塗り分け、福祉ページは小分類で描き分けます」）。

**各ページの凡例で、その色が何を指すかを明示します。**
