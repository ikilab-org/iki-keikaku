# 全計画の洗い出しと、分類・関係の整理（設計）

作成 2026-08-12 ／ 対象 `data/plans.yml`・`data/schema.md`・`sources/POLICY.md`・`tools/`

README「フェーズ2」の第1段階、**「`data/plans.yml` にすべての計画を入れる」**の設計です。
図表の生成（第2段階）はこの範囲に含めません。

---

## 1. なぜ今これをやるか

現在の `data/plans.yml` は31件（市22・社協1・県8）で、うち5件は `status: unknown` の枠だけです。
福祉分野は深く入っている一方、産業・教育・環境・インフラ・行財政は事実上ゼロです。

このまま分野を足していくと、次の2点で行き詰まります。

1. **分類が破綻する。** `category` は福祉を5つに割っている（`fukushi` `shougai` `kourei` `kodomo` `iryou` `kenkou`）
   のに対し、それ以外は `jyoui` と `other` の2つしかありません。全市に広げると新しい分野がすべて
   `other` に入ります
2. **関係がデータに載っていない。** 県計画が8件入っているのに、**市計画から県計画へ張られた参照が1本もありません。**
   「県計画との整合」は現在HTMLの本文にしか存在せず、機械的に辿れません

## 2. 決めたこと

| 論点 | 決定 |
|---|---|
| 今回の成果物 | データ整備を最優先。ページ化は次回 |
| 収録範囲 | 市が公表している行政計画すべて（法定・任意を問わない）。名称が「ビジョン」「戦略」「方針」「プラン」でも、計画として機能するものは含む |
| 実施機関 | 市長部局・教育委員会・行政委員会・消防をすべて含む（→ 5.1） |
| 除外するもの | 年度単位の事業計画、予算、個別事業の実施要綱、市以外の団体が策定する計画 |
| 調査の深さ | 2段階。全件の骨格を先に入れ、根拠法・所管課・関係は `todo:` を立てて主要計画から埋める |
| 分野の分類 | 2階層（`domain` 大分類＋`category` 小分類）。配色は `domain` 側 |
| 追加する軸 | `statutory`（法定性）・`tier`（計画の階層）・`agency`（実施機関） |
| 洗い出しの主軸 | 組織ごと巡回（対象機関ごとに起点の規程を分ける）。パブコメ一覧・総合計画の関連計画一覧・附属機関の設置条例で交差検証 |
| 検証 | `tools/validate.mjs` を新設 |

## 3. 分類の設計

### 3.1 分野を2階層にする

`categories` の小分類はそのまま残し、上に `domains` を置きます。

```yaml
domains:
  fukushi: { label: 健康・福祉, slot: 1 }
  # …（顔ぶれは 3.2 の手順で確定させる）

categories:
  shougai: { label: 障がい福祉, domain: fukushi }
  # slot は categories から取り除き、domains へ移す
```

**`slot`（配色の割り当て番号）を `categories` から `domains` へ移します。** 小分類は20前後になる見込みで、
識別可能な色を割り当てられないためです。ハブページは大分類で塗り分け、福祉ページは小分類で描き分けます。

`data/schema.md` は「`slot` の番号を勝手に入れ替えない（色覚特性を考慮した並び順で検証済み）」としています。
今回は色を持つ対象そのものが変わるため、**`domains` が確定した時点で配色の検証を1回やり直します。**
既存 `categories` の `slot` 1〜7 は、この移動をもって役目を終えます。

### 3.2 `domains` の顔ぶれは、骨格収集の後に確定させる

実在する計画を見る前に分野名を決めると、中身が1件もない分野を作って後で畳むことになります。
骨格収集が終わった時点で、次のルールで確定させます。

1. **1件しか入らない `domain` は作らない。** 近い分野に寄せる
2. **8つ以下に収める。** 配色で識別できる上限
3. 第4次総合計画の基本目標と対応が取れるものは、**その名称と粒度を優先する**（市自身の体系に合わせる）

作業中は暫定として `fukushi`（健康・福祉）・`sougou`（市政総論）・`kyouiku`（教育・文化）・
`sangyou`（産業・雇用）・`kurashi`（生活環境）・`bousai`（防災・安全）・`kiban`（都市基盤・交通）・
`gyouzaisei`（行財政運営）の8つを使い、収集完了後に上のルールで見直します。

### 3.3 `statutory` — 法定性

「市が省略できない計画はどれか」を示します。`laws` の有無とは一致しません。
根拠法があっても努力義務にとどまるもの、法律ではなく国の通知で求められるものがあるためです。

| 値 | 意味 | 条文の型 |
|---|---|---|
| `mandatory` | 法定義務 | 「定めるものとする」「策定しなければならない」 |
| `effort` | 努力義務 | 「定めるよう努めるものとする」 |
| `request` | 国の要請・通知 | 法律ではなく通知・指針で策定を求められる（公共施設等総合管理計画など） |
| `permissive` | 許容規定 | 「策定することができる」。根拠規定はあるが義務ではない |
| `voluntary` | 任意 | 法令上の根拠なし。市の独自判断 |

`permissive` は当初4値で設計したあと、Task 9 で**次世代育成支援対策推進法8条1項が
「市町村行動計画を策定することができる」という許容規定**であることが分かって追加しました。
根拠規定があることと、全く無いこと（`voluntary`）は区別する価値があります。

**判定は条文の文言を確認してから書きます。** 確認前は書かず、`todo:` に残します（→ 6.1）。

#### 一体策定された計画は、根拠法ごとに義務の強さが違う

`statutory` を計画に1つだけ付けると、**どの法定計画についての判定なのかが失われます。**
実例があります。`kodomo-1`（壱岐市こども計画）は次を一体化しています。

| 一体化された計画 | 根拠 | 条文 | 義務 |
|---|---|---|---|
| 子ども・子育て支援事業計画 | 子ども・子育て支援法61条1項 | 「定めるものとする」 | `mandatory` |
| こども計画 | こども基本法10条2項 | 「定めるよう努めるものとする」 | `effort` |

そこで **`laws` を「根拠法＋義務」の対応表に拡張し、`statutory` はそこからの集約値**とします。

```yaml
laws:
  - { law: 子ども・子育て支援法61条1項, obligation: mandatory }
  - { law: こども基本法10条2項, obligation: effort }
statutory: mandatory        # 集約値
```

**集約規則は「最も強い義務を採る」**（`mandatory` > `effort` > `request` > `permissive` > `voluntary`）。

`request` を `permissive` より上に置くのは、**国の通知で策定を求められる計画のほうが、
法律が「できる」と言うだけの計画より実務上は省略されにくい**ためです。`permissive` を `voluntary`
より上に置くのは、根拠規定があるかないかの差です。
「この計画は市が省略できるか」という問いに答えるためのフィールドなので、
1本でも義務があれば省略できない、という意味になります。

`laws` は**文字列のままでも書けます**（`- 介護保険法117条`）。その場合 `obligation` は未判定として扱い、
`statutory` の集約検査の対象外になります。既存の記述を一括で書き換える必要はありません。

構成計画が独自のページや前身計画を持つ場合は、**従来どおり `includes` / `embedded_in` で個別エントリを立てます**
（`seinen-kouken`・`saihan-boushi` と同じ形）。`laws` の拡張は、個別エントリを立てるまでもない場合の受け皿です。
両方書いた場合、個別エントリ側の `statutory` が詳細、親の `statutory` が集約値になります。

### 3.4 `tier` — 計画の階層

体系図の縦軸です。`parent` だけでは、どの高さに置くべきかが決まりません。

| 値 | 意味 | 例 |
|---|---|---|
| `sougou` | 市全体を対象とする総合的な計画 | 総合計画、過疎地域持続的発展計画 |
| `bumon` | 部門別の基本計画（分野の方針を定める） | 地域福祉計画、障がい者計画、健康いき21 |
| `kobetsu` | 個別計画（法定の事業計画。数値目標と期間を持つ） | 介護保険事業計画、障がい福祉計画、データヘルス計画 |
| `jisshi` | 実施計画・行動計画（事業単位、期間が短い） | 新型インフルエンザ等対策行動計画、国民保護計画 |
| `shisetsu` | 施設・財産の管理計画 | 公共施設等総合管理計画、個別施設計画 |

### 3.5 `agency` — 実施機関

`level: municipal` の計画にのみ付けます。社会福祉協議会は市の機関ではないため、
従来どおり `level: council` で区別します。

**既定は `mayor` で、省略できます。** 市長部局の計画が大半を占めるため、全件に書くと冗長になるだけです。
`mayor` 以外の実施機関のときだけ書きます。

| 値 | 意味 | 組織の根拠 |
|---|---|---|
| `mayor` | 市長部局（**省略時の既定**） | 行政組織規則 |
| `education` | 教育委員会 | 教育委員会事務局組織規則 |
| `fire` | 消防本部 | 消防本部の組織規程 |
| `agri` | 農業委員会 | 農業委員会の組織規程 |
| `assembly` | 議会 | 議会事務局の組織規程 |
| `election` | 選挙管理委員会 | 選挙管理委員会事務局の組織規程 |
| `audit` | 監査委員 | 監査委員事務局の組織規程 |

**値は 5.1 の巡回対象と1対1で対応させます。** 巡回対象にありながら enum に値がないと、
該当する計画が見つかったときに `agency` を省略して市長部局と誤認させるか、enum違反にするかの
どちらかになります。`election` と `audit` は計画を持たない可能性が高いものの、
**巡回する以上は値を用意しておきます。**

**5.1 の表に機関を追加したら、同時にこの enum にも値を追加します。** 市長部局以外の実施機関が
新たに見つかった場合（公平委員会、固定資産評価審査委員会など）、
`agency` を省略して既定の `mayor` に落とすことは**しません。**

**省略は常に「市長部局である」という積極的な主張です。**「実施機関が未確定」という意味では使いません。
6.1 は未調査を「フィールドの欠落＋`todo:`」で表しますが、`agency` は既定値を持つため、
欠落が未調査を表せない唯一のフィールドになります。

これで困らないのは、**5.1 の組織ごと巡回では、どの組織のページで見つけたかがそのまま実施機関になる**
ためです。発見の時点で実施機関は確定しています。5.2 の交差検証で先に名称だけを見つけた計画については、
**所属組織を特定してからエントリに骨格を入れます**（`url` を確定させる作業と同じ工程になります）。

**当初の設計にあった `water`（上下水道）と `hospital`（病院事業）は削除しました。**
上下水道課は行政組織規則の建設部に含まれており市長部局です。
また壱岐市民病院は2015年に長崎県病院企業団へ移管され、**市に病院事業は存在しません**
（現在の長崎県壱岐病院は県の病院企業団立で、その中期経営計画は市の計画ではない）。

## 4. 関係の設計

### 4.1 `parent` の意味を限定する

現在 `parent` が2つの意味で使われています。

- `chiiki-fukushi-3` → `sougou-4`（位置づけ上の上位計画）
- `seinen-kouken` → `chiiki-fukushi-3`（1冊に包含されている）

後者は `embedded_in` にも同じ値が入っており、冗長です。**`parent` は位置づけ上の上位計画に限定し、
包含は `embedded_in` に一本化します。** `seinen-kouken` と `saihan-boushi` の `parent` を削除します。

### 4.2 `conforms_to` を新設する

市計画が整合・調和を求められる国・県計画を指します。**法令上の要請があるものに限ります。**
それ以外の参考関係は `related` に入れます。

**この設計の初版は、例として「介護保険法117条4項の都道府県計画との整合」「社会福祉法107条の
都道府県地域福祉支援計画との調和」を挙げていました。どちらも条文にない記述でした。**
Task 8 で8件の条文を実際に確認したところ、次が分かっています。

- 介護保険法117条には「都道府県介護保険事業支援計画」という語が**一度も出てきません。**
  117条11項の調和条項が対象とするのは市町村地域福祉計画など**同じ市町村の他の計画**です
- 社会福祉法108条は、都道府県地域福祉支援計画を「**市町村地域福祉計画の達成に資するため**」の
  ものと定めています。**県が市を支える向き**であり、市が県に合わせる規定ではありません
- 8件のうち法令上の整合が明記されていたのは**障害者基本法11条3項の1件だけ**でした
  （「都道府県障害者計画を基本とするとともに」）

**市町村計画が県計画との整合を法令上求められる場面は、想定より大幅に少ないということです。**
多くは国の基本指針・大綱を介して間接的に結ばれており、県計画はむしろ市町村計画を支援する側に置かれています。
`conforms_to` を書くときは、必ず条文の文言を確認してください。

```yaml
conforms_to: [pref-chouju-9]
```

### 4.3 関係の一覧（確定形）

| フィールド | 向き | 意味 |
|---|---|---|
| `parent` | 下→上 | 位置づけ上の上位計画。原則 `sougou-4` |
| `includes` | 親→子 | 一体策定により包含している法定計画 |
| `embedded_in` | 子→親 | `includes` の逆。両方を書く |
| `conforms_to` | 市→県・国 | 法令上、整合・調和が求められる計画 |
| `related` | **無向** | 上記以外の連携。片側にだけ書く（→ 4.4） |
| `predecessors` | 現→過去 | 前期計画（新しい順） |
| `successor` | 現→次期 | 次期計画（オブジェクト。id ではない） |

### 4.4 `related` は無向の関係とする

「双方向の関係だが片側だけ書けばよい」とすると、**片側にしかない記載が相互関係なのか一方向の参照なのかを
機械的に区別できません。** 体系図を生成するときに辺の向きが決まらなくなります。

`related` を**無向（undirected）と定義**して解消します。`A.related` に B があることは
「A と B に連携がある」だけを意味し、向きを持ちません。辺の集合は両者の和集合を重複除去して作ります。

- **片側にだけ書きます。** 両側に書かれていたら冗長なので `validate` が **warn** で報せます。
  無向辺として解釈すれば意味は壊れず、辺の集合も変わらないため error にはしません（→ 7.3）
- **向きのある関係は既存フィールドが担当します。** 上下＝`parent`、包含＝`includes` / `embedded_in`、
  法令上の整合＝`conforms_to`。これらに当てはまらないものだけが `related` に入ります
- したがって `related` に一方向の参照という状態は存在せず、曖昧さは生じません

現在のデータはすべて片側記載です（`chiiki-fukushi-3` から4件）。この定義で追加の書き換えは要りません。

## 5. 洗い出しの手順

市サイトの `/shisei/machidukuri/keikaku/` は**計画の総覧ではありません。**
2026-08-12 時点で5節と数記事しかなく、実体は各課のページ（`/soshiki/...`）に散在しています。
単一の情報源では必ず漏れるため、主軸と交差検証を組み合わせます。

### 5.1 主軸 — 組織ごと巡回

各組織のページを順に見ます。`sources/POLICY.md`「所管課は例規集で確認する」の方針と一致し、
**計画の発見と `department` の確定が同時に進む**のが利点です。

#### 起点は1つではない

[行政組織規則](https://www.city.iki.nagasaki.jp/section/reiki/reiki_honbun/r014RG00000018.html)
第1条は、この規則の対象を次のように限定しています。

> 市長及び会計管理者の権限に属する事務並びに市長が設置する行政機関の事務を処理するために必要な組織

つまり**この規則だけを起点にすると市長部局しか巡回できません。** 教育委員会・行政委員会・議会・消防は
別の組織規程に基づくため、対象機関ごとに起点を分けます。

| 対象機関 | 起点となる規程 | 備考 |
|---|---|---|
| 市長部局 | [行政組織規則](https://www.city.iki.nagasaki.jp/section/reiki/reiki_honbun/r014RG00000018.html) 第3条 | 総務部・地域振興部・市民部・保健環境部・農林水産部・産業推進部・建設部。**上下水道課は建設部に含まれる** |
| 教育委員会 | [教育委員会事務局組織規則](https://www.city.iki.nagasaki.jp/reiki/reiki_honbun/r014RG00000190.html) | 教育総務課・学校教育課・社会教育課 |
| 消防 | 消防本部の組織規程 | 例規集で規程名を確定させてから巡回する |
| 農業委員会 | 農業委員会の組織規程 | 同上 |
| 議会 | 議会事務局の組織規程 | 同上 |
| 選挙管理委員会・監査委員 | 各事務局の組織規程 | 計画を持たない可能性が高いが、**確認して「なし」と記録する** |

**病院事業は対象外です。** 壱岐市民病院は2015年に長崎県病院企業団へ移管され、市の組織ではなくなりました。
市の[組織一覧](https://www.city.iki.nagasaki.jp/soshiki/index.html)にも行政組織規則にも病院は存在しません。

#### 組織一覧ページを起点にしない

市の組織一覧ページは規則と表記が食い違います。2026-08-12 時点で、一覧は「水道課」、規則は「上下水道課」でした。
`sources/POLICY.md` の「告知ページは組織改編後に更新されないことがある、例規集が一次資料」がここでも当てはまります。
**組織一覧は巡回先を見つける補助として使い、組織の正式名称と分掌は規程で確定させます。**

### 5.2 交差検証 — 漏れの検出

| 情報源 | 拾えるもの | 落ちるもの |
|---|---|---|
| パブリックコメント実施状況の一覧 | 策定・改定の時期。名称の正式表記 | パブコメを経ない計画、任意計画 |
| 第4次総合計画本体の関連計画一覧・体系図 | 市自身が認識している体系 | 総合計画の策定後にできた計画 |
| 例規集の附属機関設置条例（○○審議会・○○協議会） | 消えない根拠。審議会を置く計画 | 審議会を置かない計画 |

### 5.3 記録すること

**どの情報源で拾えて、どれでは拾えなかったかを残します。** 次回の調査で同じ手順を再現でき、
「網羅した」と言える根拠になります。`sources/POLICY.md` に節を追加し、巡回した課の一覧と実施日を記録します。

## 6. データ投入の段取り

### 6.1 未調査の表し方は1つに統一する

現在、未調査を表す手段が `status: unknown` と `todo:` の2つあり、どちらを使うかが決まっていません。
投入する人と `validate` で判定が割れるため、次に統一します。

| 表すもの | 書き方 |
|---|---|
| **フィールドが未調査** | **そのフィールドを書かない（欠落）＋ `todo:` に何が未調査かを書く** |
| **計画全体が未調査** | `status: unknown`（`todo:` も併記する） |

**空文字や `null` で未調査を表しません。** `null` は「調査した結果、値が存在しない」という意味で使います
（例: `bousai` は随時修正のため `period: { start: null, end: null }`）。

`todo:` は `tools/expiring.mjs` が「未調査の項目」として一覧に出すため、**書き忘れると追跡から漏れます。**

### 6.2 第1段階 — 全件の骨格

**条文やPDF本文を読まなくても、掲載ページだけで確定できる項目**に限ります。
`statutory` と `laws` と `department` は条文・例規の確認が要るため、第1段階には含めません（3.3 と矛盾させない）。

| 区分 | フィールド |
|---|---|
| 必須（欠けたら `validate` が error） | `id` `name` `level` `domain` `category` `tier` `status` |
| 条件付き必須（→ 7.2） | `period` `url` |
| 任意（既定値あり） | `agency`（既定 `mayor`。市長部局なら書かない） |
| 第2段階に送る | `statutory` `laws` `department` `adopted` `pdf` 各種の関係 |

`tier` を必須に含めるのは、**体系図の縦位置がこれで決まり、後から一括で判定できないため**です。
掲載ページの名称と位置づけを見た時点で判断できます。

### 6.3 第2段階 — 深掘り

`laws`（条項まで）・`department`（行政組織規則を根拠に）・`parent` / `includes` / `embedded_in` /
`conforms_to` / `related`・`adopted`・`pdf`・`successor` を、次の順で埋めます。

1. 改定期が近い計画（`tools/expiring.mjs` が拾うもの）
2. `tier: sougou` と `tier: bumon`（体系図の骨格になる）
3. その他

### 6.4 既存31件の扱い

新フィールド（`domain` / `statutory` / `tier` / `agency`）を遡って付与し、4.1 の `parent` 重複を解消し、
市計画から県計画への `conforms_to` を張ります。**既存の記述内容は変更しません。**

## 7. 検証（`tools/validate.mjs` 新設）

### 7.1 依存を増やさない

`.github/workflows/` は `npm install` を実行せず `node tools/*.mjs` を直接叩きます。
README も「Node 18 以降であれば追加の依存なしで動く」と書いています。**この性質を壊しません。**

既存の `linkcheck.mjs` と `expiring.mjs` は、それぞれ正規表現の簡易パーサを持っています。
URLの抽出と単純なスカラーの読み取りには足りますが、**参照整合の検査には配列（`includes: [a, b]`）の
解釈が要ります。** そこで `plans.yml` が実際に使う範囲だけを扱う最小パーサを `tools/yaml.mjs` に切り出し、
`validate.mjs` から使います。

対応する構文はこれだけです。ネストしたマップ、マップの配列、フロー形式のマップ `{ start: 2024, end: 2026 }`、
フロー形式の配列 `[a, b]`、折りたたみブロックスカラー `>-`、コメント、引用符つき文字列。

### 7.2 error と warn を分ける

必須フィールドが欠けていても `todo:` があれば、それは**未調査だと宣言されている状態**であって誤りではありません。
一方 `todo:` もなく欠けているなら、記入漏れです。この2つを区別しないと、
「投入途中だから全部赤」か「欠落を見逃す」かのどちらかになります。

| 種別 | 条件 | exit code |
|---|---|---|
| **error** | 整合性の破れ（参照切れ・enum違反・`id` 重複）、または**必須フィールドが `todo:` なしで欠落** | `--fail-on-error` で 1 |
| **warn** | 必須フィールドが欠落しているが `todo:` がある（明示的な猶予）、または意味を壊さない冗長な記述 | 0 |

### 7.3 検査項目

**構造の検査（常に error）**

| 検査 | 例 |
|---|---|
| `id` の重複 | 同じ `id` が2回出る |
| `id` の書式 | `^[a-z0-9-]+$` に合わない |
| enum 違反 | `status: 現行` のような未定義の値。`level` `status` `tier` `statutory` `agency` が対象 |
| 未定義のキー参照 | `domain` / `category` が `domains` / `categories` にない |
| `category` と `domain` の不一致 | `category` に紐づく `domain` と、計画の `domain` が違う |
| 参照切れ | `parent` `includes` `embedded_in` `conforms_to` `related` `predecessors` の指す `id` が存在しない |
| 包含の片方向 | `A.includes` に B があるのに `B.embedded_in` が A でない |
| `parent` と `embedded_in` の重複 | 同じ値を指している（4.1 の型） |
| `conforms_to` の宛先 | `level: municipal` から `municipal` を指している（県・国が対象） |
| 集約値の不一致 | `laws[].obligation` の最強値と `statutory` が違う（3.3 の集約規則） |
| 期間の逆転 | `period.start > period.end` |
| 日付の書式 | `adopted` / `public_comment` が `YYYY-MM` でない |
| status と期間の矛盾 | `expired` なのに `end` が将来、`current` なのに `end` が過去 |

**正規化の検査（常に warn）**

意味は壊れていないが、書き方が冗長なものです。**辺の集合が変わらないので error にしません。**

| 検査 | 例 |
|---|---|
| `related` の両側記載 | A と B の双方に書かれている（4.4 により片側でよい） |

**骨格の検査（`todo:` があれば warn、なければ error）**

6.2 の投入要件をそのまま検査します。**これがないと、`tier` や `period` が大量に欠けたまま完了条件を通過します。**

| フィールド | 必須となる条件 |
|---|---|
| `id` `name` `level` `status` | 常に |
| `domain` `category` `tier` | `level` が `municipal` または `council`（県・国の計画は文脈として持つだけなので任意） |
| `period` | 上記に同じ。ただし `status` が `planned` / `unknown` のものは免除 |
| `url` | 上記に同じ。ただし **`embedded_in` があるもの**（一体策定の構成計画は親のページを共有する）、および **`pdf` か `sources` で出典が確保されているもの**は免除 |
| `agency` | 必須にしない（既定 `mayor`。書かれていれば enum を検査するのみ） |
| `statutory` `laws` `department` | 第1段階では必須にしない（第2段階の項目） |

`url` の免除は既存データで実際に効きます。2つとも実在の型です。

- `seinen-kouken` と `saihan-boushi` は `chiiki-fukushi-3` の計画書に包含されており、単独の掲載ページがない
- `kourei-7` と `kourei-8` は**計画ページ側の単独PDFが削除済み**で、議案書PDF（`sources`）が唯一の出典。
  `sources/POLICY.md` が中心事例として扱っている状態そのもの。ここに `todo:` を付けるのは
  「未調査」という誤った宣言になる

`--json` で機械可読に出します（既存2ツールと同じ流儀）。

### 7.4 CI

`.github/workflows/` に `validate` を足すかは、**このデータ整備が一段落してから判断します。**
投入の途中は `todo:` と欠落が大量にあり、常時赤になっても意味がないためです。
