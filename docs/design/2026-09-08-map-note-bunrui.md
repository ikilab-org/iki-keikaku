# コンテンツを「マップ」と「ノート」に分け、サイト名を改める（設計）

作成 2026-09-08 ／ 対象 `index.html`・`plans/*/index.html`・`tools/build.mjs`・`tools/pages.test.mjs`・
`tools/og/cards.html`・`assets/og*.png`・`README.md`

コードとデータには手を入れません。**呼び名と、それを表示している箇所だけの変更**です。

---

## 1. なぜ今これをやるか

**サイト名が中身を言い当てなくなりました。** 「壱岐市 計画マップ」を名乗って始めましたが、
公開している4ページのうち、マップと呼べるのは `plans/all/` の1枚だけです。

| ページ | していること |
|---|---|
| `plans/all/` | 78件を階層・期間・分野で並べる |
| `plans/fukushi/` | 地域福祉計画を軸に体系と時系列を整理する |
| `plans/kaigo-7-9/` | 見込値と決算・統計の実績を突き合わせる |
| `plans/koutsuu/` | 補助金と輸送人員から1乗車あたりの公費を出す |

下2本は「228円 → 468円」のような**結論を持っています**。地図は結論を持ちません。
`plans/fukushi/` は関係の図示という点でマップに近いのですが、手書きで、扱う範囲は福祉分野に限られます。

これから増えるものを見ても、ズレは広がる一方です。次の深掘り先は公共施設等総合管理計画で、
[`docs/README.md`](../README.md) には市への照会記録やパブリックコメントの提出内容を置く想定も書いてあります。
どれも「マップ」には収まりません。

## 2. 決めたこと

| 論点 | 決定 |
|---|---|
| サイト名 | **「壱岐市 計画マップ」→「壱岐市 計画資料集」** |
| 分類 | **マップとノートの2つ。** マップは `plans/all/` の1枚だけ、残りはすべてノート |
| 定義の強さ | **非対称。** マップは狭く縛り、ノートは器として残り全部を受ける（3.3） |
| 表示の仕方 | **ハブの見出しを2節に割る。** カードごとのラベルは付けない（5章） |
| URL | **変えない。** `/plans/` のまま。マップとノートでディレクトリは分けない |
| ドメイン | **変えない。** `keikaku.ikilab.org` のまま |

## 3. 分類

### 3.1 マップ ― 定義をきつく縛る

> 壱岐市に関わる計画を全件並べ、階層と計画期間で俯瞰します。構造化データから生成しているので
> 網羅的で常に最新な代わりに、個々の中身には踏み込みません。

「全件・構造だけ・`data/plans.yml` からの生成」の3つを満たすものだけをマップと呼びます。
いま該当するのは `plans/all/` だけです。

**「生成物であること」は定義ではなく、いまたまたま線が一致しているだけです。** 将来、網羅的な図を
手書きで作ったなら、それもマップです。縛りたいのは網羅性と、中身に踏み込まないことのほうです。

### 3.2 ノート ― 器にする

> 範囲を絞って書いたものです。計画どうしの関係を整理したり、計画書の見込値を決算や統計と
> 突き合わせたりします。何を扱うかはページごとに違います。

`plans/fukushi/`・`plans/kaigo-7-9/`・`plans/koutsuu/` の3本。次の公共施設等総合管理計画もここに入ります。

### 3.3 なぜ非対称にするか

ノート側を厳密に定義したくなりますが、しません。「検証」と定義すれば `plans/fukushi/` の体系整理が外れ、
「深掘り」と定義すれば照会記録やパブコメが外れます。**器は、次に入れたいものを弾かないことに価値があります。**

読み手にとっても、きつく縛られているのはマップのほうです。「全件ある」「線は引かれていない」
「中身には踏み込んでいない」を約束できることに意味があり、ノートは開いてみないと分からなくてかまいません。

### 3.4 線を引かないことは、この分類と整合する

全体マップに計画間の線を引かない判断は
[2026-08-13 の設計 3.1](2026-08-13-zenkeikaku-zuhyou.md) で決めたとおりです。78件に対して
`parent` は8本しかなく、線を引くと大半が孤立した図になります。これは関係が無いのではなく
**まだ調べていない**（`todo` 31件）ためで、調査の穴が「関係の不在」という誤った主張に見えてしまいます。

分類を分けると、この判断の意味がはっきりします。**全体には線を引けないが、ノートの中でなら
範囲を絞って引ける。** `plans/fukushi/` の体系図がすでにそれをやっています。

## 4. サイト名

### 4.1 「計画資料集」を選んだ理由

器の語なので、マップ1枚とノート数本をそのまま受けます。決め手は、
`index.html` と `README.md` の説明文が**すでに「資料集です」と自称していた**ことです。
名前と本文が一致し、新しい語を1つも増やさずに済みます。

### 4.2 採らなかった案

| 案 | 採らなかった理由 |
|---|---|
| 壱岐市 計画ノート | マップが中に入って入れ子が逆転する。`kaigo-7-9`・`koutsuu` の検証の重さに対して語が軽い |
| 壱岐市の計画を読む | 姿勢は出るが、固有名詞として呼びにくく引用されにくい |
| 壱岐市の行政計画 | **市の公式ページと誤認されやすい。** [`DISCLAIMER.md`](../../DISCLAIMER.md) の立場と逆を向く |

最後の点は重要です。いまの名前に「マップ」が入っていることは、これが独立した二次資料だという合図にも
なっていました。**種別語を落とすとその機能が消えます。**「資料集」はその役割を引き継げます。

### 4.3 クレジット表記が変わる

**このサイトでは、名前がそのまま帰属表示の文字列です。**
`about/license/` と [`NOTICE.md`](../../NOTICE.md) は、利用者に次のクレジット例を示しています。

```
出典：壱岐市 計画マップ（IKILAB）CC BY 4.0
```

改名すると、すでに旧名で引用した人のクレジットが宙に浮きます。改名を止める理由にはしません
（資料が増えてからのほうが影響は大きい）が、**旧名を追える一文を残します。**

- `about/license/` に「2026年9月まで『壱岐市 計画マップ』の名称で公開していました」の一文を置く
- `CHANGELOG.md` に改名を記録する
- クレジット例は新名に差し替える（`about/license/` 3か所、`NOTICE.md` 1か所）

CC BY 4.0 は指定された方法での帰属表示を求めるもので、指定する名前を変えること自体は妨げられません。
旧名での既存のクレジットも、対応が追える限り有効です。

## 5. ハブの構成

`index.html` の `<h2>公開中のマップ</h2>` と、その下の1つの `.cards` を、2節に割ります。

```
<h2>マップ</h2>       + 定義文（3.1）  → カード1枚（plans/all/）
<h2>ノート</h2>       + 定義文（3.2）  → カード3枚（fukushi, kaigo-7-9, koutsuu）
```

**カードごとの型ラベルは付けません。** カードの `.k` には現在「全分野」「福祉分野」「介護保険」「公共交通」と
分野名が入っています。ここに型を足すと情報が二重になり、`.k` の役割も壊れます。型は見出しが担います。

## 6. あわせて直す記述のズレ

呼び名を整理するついでに、前から合っていなかった2か所を直します。

### 6.1 「計画どうしの関係を図にして」

`index.html` のヘッダー説明文と `README.md` の冒頭が、この資料集を
「計画どうしの関係を図にし、個別の計画を深掘りできるようにした資料集」と説明しています。
**マップは線を引かないと決めているので、これは実物とズレています。**

マップとノートの2本立てを説明する文に差し替えます。

### 6.2 `plans/fukushi/` のバッジ

バッジが「長崎県壱岐市 ／ 計画体系マップ」で、**ノートに分類したページが自分をマップと名乗っています。**
他の2本は「介護保険事業計画の検証」「地域公共交通計画の読み直し」と*対象＋作業*で揃っているので、
「**地域福祉計画の体系整理**」にします。ハブのカード見出しとも一致します。

## 8. やらないこと

- **URL構造の変更。** `/plans/` を `/maps/` と `/notes/` に割るのは、リダイレクトの手当てが要るうえ、
  分類が固まってからで足ります。ディレクトリ名は現状維持
- **ドメインの変更。** `keikaku.ikilab.org` はそのまま
- **`data/plans.yml` のスキーマ変更。** 呼び名の話とは別件（9章の積み残し）
- **ノート本文の書き換え。** 触るのは 6.2 のバッジ1か所だけ。各ページの見出しや本文はそのまま
- **`docs/design/` の過去2件の書き換え。** 当時そう呼んでいたという記録なので残す
- **新しいノートの追加。** 公共施設等総合管理計画の深掘りは、この設計の完了後に別途

## 9. 積み残し

**「上位方針に基づく下位計画」を表すフィールドがありません。** 施設・財産管理の5本
（`kyoryo-choju`・`douro-norimen-iji`・`douro-tunnel-iji`・`koei-jutaku-choju`・`noudou-shisetsu-kobetsu`）は
`related: [kokyoshisetsu-kobetsu]` を張っていますが、`related` は**無向の「その他の連携」**です。
実際の関係は「基づく」という向きのあるものです。

`data/schema.md` の既存フィールドはどれも当たりません。`parent` は「位置づけ上の上位計画。原則 `sougou-4`」、
`conforms_to` は市→県・国、`includes`/`embedded_in` は一体策定による包含。
**日本の行政計画でいちばん普通のこの関係だけが、無向の雑多枠に落ちています。**

`kokyoshisetsu-sougou` と `kokyoshisetsu-kobetsu` のあいだにも線がありません
（`notes` に「総合管理計画の基本方針に基づき」と書いてあるのに、フィールドとしては張られていない）。

公共施設等総合管理計画のノートは、この一角の線を引くことが中身になります。
**着手前にスキーマ側を決める必要があります。** 別の設計として扱います。
